# Choose the visual from the relationship

Use this as a repertoire, not a sequence or a set of mandatory templates. Adapt geometries and labels to the case. Prefer native objects and controlled variation within the deck's system.

| Slide job | Suggested composition | Content and visual logic | Failure to avoid |
|---|---|---|---|
| Executive answer | Narrow context strip + 2–3 solution rows + impact/ask column | Decision, chosen moves, why they work, expected outcome with status | A contents page masquerading as a recommendation |
| Diagnosis | 60% evidence chart + 40% mechanism/implication | Show the important gap and explain its operational cause | Many KPIs with no conclusion; confusing association with causation |
| Root-cause chain | 3–5 connected stages + small evidence tags | Cause → friction → consequence; explicitly label hypotheses | Decorative arrows between unrelated issues |
| Portfolio/segment comparison | Native table with 3–5 columns and limited rows + implication strip | Use consistent comparison dimensions; highlight what changes the intervention | Calling an unscored text table a quantitative heatmap |
| Options and choice | Criteria-by-option matrix + selection rationale | Disclose weights/scores if supplied; show material trade-offs | Invented precision or making all rejected choices weak |
| Solution architecture | 3 named pillars or layered operating model | Each pillar has a distinct mechanism and linked outcome; show dependencies | Slogans with no accountabilities or repeated three-card layouts |
| Parallel operating paths | Two swimlanes + a boundary/gate + actor rail | Separate data/actions/owners and show permitted handoffs | Connectors crossing privacy or decision boundaries accidentally |
| Persona/segment experience | 2–3 rows: need → tailored action → outcome | Use differences that affect service/design; label illustrative personas | Stereotypes or long invented first-person quotes |
| Journey/funnel | 3–5 stages + friction markers + interventions | A funnel needs consistent starting population and conversion bases | Funnel shape for a list that does not narrow |
| Initiative mechanism | Dominant process + owner/resource box + success gate | Trigger → action → handoff → result; retain operating detail | A generic “what/why/benefit” page without how |
| Governance | Compact decision-rights table + escalation path | State who decides, executes, assures, and can stop | Everyone accountable; legalistic microtext |
| Roadmap | Native Gantt/swimlanes + milestone/gate strip | Show dependencies, owner, period, deliverable, and scale decision | Coloured bars with no milestones or exit conditions |
| Economics | Native bridge/bar chart or compact model table + assumptions column | Comparable period; costs vs benefits; range/ROI/gate as appropriate | Revenue treated as profit; decorative donut with unrelated totals |
| Pilot proof | KPI scorecard + decision gate | Baseline → proposed threshold → owner → response if missed | Targets shown as forecasts or green ticks without evidence |
| Risks | 3–4 risk–trigger–mitigation–owner rows | Prioritize recommendation-changing risks; integrate stop conditions | A colourful risk matrix with invented likelihoods |
| Closing ask | Recommendation + resource request + immediate steps + gate | Make the decision and first accountable action explicit | “Thank you” replacing a substantive conclusion |

## Make a distinctive diagram

Start with nouns and verbs from the playbook. Identify the scarce resource, actor, boundary, feedback, or decision that makes the case distinctive. Encode that relationship in the geometry.

Example: if a programme has separate team-level workload actions and confidential individual support, use two labelled lanes separated by a privacy boundary. Put responsible humans beside each lane and a capacity gate before referral. The boundary and gate carry the argument; icons merely help navigation.

Example: if multiple businesses need the same capabilities at different depths, combine a shared capability spine with business-specific depth/priority cells and decision owners. Do not replace the operating distinction with eight identical decorative circles.

Do not reuse these examples automatically in unrelated cases. A retail channel case might need a demand-to-fulfilment journey; a pricing case may need segment economics; a manufacturing case may need a bottleneck flow.

## Chart choice and safeguards

| Relationship | Preferred chart |
|---|---|
| Compare categories | Sorted bars; clustered bars for a small number of series |
| Change over time | Line chart with dates and consistent intervals |
| Before/after two values | Paired bars or labelled dumbbell; show baseline and target status |
| Composition summing to a whole | Stacked bar; donut only for a few slices with clear denominator |
| Additive financial bridge | Native waterfall if supported; otherwise editable labelled bridge shapes and a calculation table |
| Trade-off | Scatter/matrix with defined axes and justified positions |
| Survey responses | Bars with n, question/base, counts or percentages; avoid unreadable pie mosaics |

Do not draw fake-data curves. Separate actual and projected series visually and in the legend. Begin bar axes at zero unless a justified exception is clearly explained. Label units and periods. Use consistent category order. Use editable data-driven charts when quantitative values exist; a conceptual process is a diagram, not a chart.
